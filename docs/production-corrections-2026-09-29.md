# Corrections fonctionnelles et UX — 29 septembre 2026

## Périmètre et architecture examinée

Application Next.js 16.2.1 / React 19, App Router, Tailwind 4. Les guides Next installés sur les composants client et `useSearchParams` ont été consultés. Les routes par rôle sont protégées par le layout dashboard et `RoleGuard`. Il n’existe pas de middleware d’authentification : les tokens sont stockés dans le navigateur et les autorisations sont vérifiées par l’API NestJS.

`AuthContext` porte la session et le profil. `api.ts` centralise les appels, les erreurs HTTP et le refresh. Les contextes `Startup`, `Application`, `Program`, `IncubationFollowups`, `User`, `Notification` et `Evaluation` portent les données métier. TanStack Query est déjà fourni au dashboard. La liste admin des candidatures l’utilise désormais avec une clé incluant utilisateur, statut, recherche, programme, page et sélection de notification. Les autres modules restent en place.

Le dépôt backend voisin a été **lu uniquement** pour vérifier les contrats. Aucun fichier backend, donnée de production, compte ou notification réelle n’a été modifié. Aucun déploiement n’a été effectué.

## BACKEND REQUIRED

**Aucun nouvel endpoint obligatoire pour les corrections livrées**, avec le contrat du dépôt backend local consulté. Vérifications nécessaires sur le déploiement de production :

1. `GET /application` : accepter `status`, `programId`, `search`, `page`, `limit`, filtrer avant pagination, renvoyer le total du même filtre dans `X-Total-Count`. Exposer cet en-tête via CORS. Si le déploiement est ancien, déployer les fonctionnalités déjà présentes localement ; le frontend ne doit pas cacher une réponse incorrecte.
2. `GET /application/:id` : permettre la lecture du dossier pour ADMIN, avec les relations startup/programme.
3. `POST /startup/:id/pitch-deck` : renvoyer le profil associé avec `id`, métadonnées du deck et statut. `PATCH /startup/:id/publish` doit confirmer `PUBLISHED` et utiliser le chemin interne réel malgré son omission des réponses API. Le code local lève déjà l’omit pour cette validation. Si la production signale « deck manquant » après association confirmée, vérifier la version déployée, l’association en base et le stockage ; aucune correction frontend ne peut réparer un fichier absent du serveur.
4. Aucun logo requis par `findPublicationBlockers` local. Une API de production qui le réclame présente un écart de contrat à résoudre explicitement.
5. `GET /users/me` et `/users` : renvoyer `isEmailVerified` indépendamment de `isActive`, comme le `USER_PUBLIC_SELECT` local. Aucune supposition de vérification si le champ manque.

**Limitation API identifiée : export CSV avec recherche texte.** `GET /reports/applications.csv` accepte `status` et `programId`, mais rejette `search` (`forbidNonWhitelisted`). Pour exporter exactement une recherche, ajouter `search` à `ReportFiltersDto` et réutiliser le filtre de la liste. En attendant, l’export reste disponible sans recherche/sélection individuelle et précise cette limite lorsqu’il est désactivé. Les filtres statut et programme sont conservés.
